# Hosting on Render

The website and the backend are hosted separately:

| Render service | What | Plan | Behaviour |
|---|---|---|---|
| `hokiebikerack` | the website (`frontend/`), a **static site** | free | loads instantly, never sleeps |
| `hokiebikerack-api` | the backend (`backend/Dockerfile`), a **web service** | free | sleeps after 15 min with no visitors, about 1 min to wake |
| `hokiebikerack-db` | PostgreSQL | free | **deleted 30 days after it's created** unless upgraded |

All three are described in [render.yaml](../../render.yaml) at the repo root (a Render "Blueprint"),
so Render creates them in one go.

## While the backend wakes up

When the API is asleep, the first visitor waits about a minute. The pages handle this
([frontend/js/backend.js](../../frontend/js/backend.js)):

- The **front page** (version chooser) is static, so it appears at once. It starts waking the
  server straight away and says "Waking the server…", then "Server ready.".
- Every **version page** (Rider, Staff, Police, Admin) shows a full-screen **Starting the Server**
  notice, with a bar and a seconds count, until the API answers. Then the page loads by itself.
  If the API answers within 0.8 s (it's awake, or running locally), the notice never appears.
- After 3 minutes the notice adds a hint: check the Render dashboard and the two addresses below.
- While a rack is plugged in by USB and connected on the Admin page, its heartbeat every
  30 s keeps the API awake.

## Before you start

1. The repo is on GitHub (it is: `main`).
2. A Render account (sign in with GitHub at render.com). The free plan needs no card.
3. **Decide about sign-in.** The site has no sign-in screen yet: the backend runs with
   `HBR_LOGIN_REQUIRED=false`, so **anyone who has the link acts as admin** (can delete racks,
   revoke cards, and so on). That's fine for a class demo with a link you don't post publicly.
   Not fine for anything real. Turning it on needs a sign-in screen in the frontend first.

## Steps

1. Render dashboard > **New** > **Blueprint**. Connect GitHub and pick the HokieBikeRack repo.
   Render reads `render.yaml` and lists the three services.
2. It asks for two values (`sync: false` in the file). Use the addresses Render will give the
   services, which are their names plus `.onrender.com`:
   - `HBR_BACKEND_URL` (on the site): `https://hokiebikerack-api.onrender.com`
   - `HBR_ALLOWED_ORIGINS` (on the API): `https://hokiebikerack.onrender.com`

   No trailing slash needed (it's ignored either way).
3. **Apply**. The database is ready in a minute or two. The API's first build takes about
   5–10 min (Maven downloads everything once). The site takes under a minute.
4. Check the real addresses: open each service on the dashboard; the URL is at the top. If a
   name was taken, Render adds a suffix (like `hokiebikerack-api-x1y2.onrender.com`). If so:
   - API's address differs: site > **Environment** > fix `HBR_BACKEND_URL` > **Save, rebuild and deploy**.
   - Site's address differs: API > **Environment** > fix `HBR_ALLOWED_ORIGINS` > **Save and deploy**.
5. Open the site's address. The front page shows "Server ready." once the API is up.
   `https://<api address>/api/v1/health` answering means the API is up.

The database starts empty: add racks on the Admin page (map > Add Rack) and connect the Uno
by USB as usual. Connect by USB needs Chrome or Edge; the site is https, so Web Serial works.

## After that

- **Updating:** push to `main`. Render redeploys what changed: `frontend/` changes rebuild only
  the site, `backend/` changes rebuild only the API (`buildFilter` in render.yaml).
- **Logs:** dashboard > `hokiebikerack-api` > **Logs**. Startup ends with "Started HokieBikeRackApplication".
- **Passwords:** `ADMIN_PASSWORD` and `VIEWER_PASSWORD` are generated by Render (API > Environment).
  They're only used once sign-in is turned on.
- **Database expiry:** the free database is deleted 30 days after it's created (Render emails
  first). Upgrade it (paid) or make a new one before then; the data doesn't carry over by itself.
- **Keeping it awake** for a demo: open the front page a minute before you present.

## Running locally is unchanged

`frontend/js/backend-url.js` holds `""`, so the pages call the server that served them, and
`mvn spring-boot:run -Dspring-boot.run.profiles=embedded` serves both at http://localhost:8080
as before. Only Render's build rewrites that file (on Render's copy, never in the repo).

## What each setting is

| Where | Setting | Meaning |
|---|---|---|
| site | `HBR_BACKEND_URL` | the API's address, written into `js/backend-url.js` at build time |
| site | headers in render.yaml | the same Content Security Policy the backend uses, plus `https://*.onrender.com` so pages may call the API |
| API | `HBR_ALLOWED_ORIGINS` | which websites' pages may call the API (CORS), comma-separated |
| API | `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD` | filled in from the database by Render |
| API | `PORT` | set by Render; the backend listens on it |
| API | `HBR_LOGIN_REQUIRED` | `false` = no sign-in, everyone is admin (see above) |
